# AI для бизнеса: от идеи до решения — дизайн интерактивного сайта

Дата: 2026-08-08
Статус: согласовано, готово к планированию реализации

## 1. Что делаем

Статический сайт-методичка на основе ТЗ (`ai_for_business.docx`): 10 разделов прозы,
квизы, финальный экзамен, два рабочих тренажёра. Всё исполняется в браузере, бэкенда нет,
телеметрии нет.

Позиционирование берём из ТЗ дословно и выносим на первый экран: методичка не учит писать
код, обучать модели или проектировать архитектуру. Она учит понимать рынок AI, говорить на
одном языке с заказчиком и инженером, находить реальные бизнес-кейсы и отличать работающее
решение от маркетингового обещания.

Аудитория: AI presales, business development, product owners, delivery managers,
руководители направлений, предприниматели, консультанты. Не для data scientists, AI
engineers, ML researchers.

Язык — русский. i18n не закладываем.

### Границы

В объёме:
- 10 разделов прозы по ~1000–1500 слов каждый;
- квиз после каждого раздела;
- финальный экзамен в двух режимах;
- тренажёр выбора класса решения (Раздел 9);
- discovery-опросник (Раздел 8);
- глоссарий с всплывающими определениями;
- прогресс чтения в localStorage;
- деплой на публичный GitHub Pages.

Вне объёма:
- собственный калькулятор экономики — вместо него ссылка на существующий
  [Inference TCO Calculator](https://kryadov.github.io/llm-hardware-calculator/);
- любой бэкенд, аккаунты, синхронизация прогресса между устройствами;
- проверка открытых текстовых ответов;
- английская версия;
- выдача сертификатов.

## 2. Стек и структура

Vite 7 + React 19 + TypeScript + Tailwind 4 + Vitest + zod. Тот же тулчейн, что в
`kryadov/llm-hardware-calculator`, чтобы не держать два разных конвейера.

Дополнительно: `@mdx-js/rollup` + `remark-gfm` — проза пишется как markdown, но допускает
React-компоненты внутри, без самодельного синтаксиса плейсхолдеров.

`vite.config.ts`: `base: '/ai-for-business-tutorial/'`.

```
src/
  content/
    01-landscape.mdx … 10-myths.mdx     проза разделов
    facts.test.ts                       проверка свежести фактов
  data/
    sections.ts                         реестр разделов: id, slug, заголовок, порядок, виджет
    quizzes/01.ts … 10.ts, exam.ts      банки вопросов
    decision-tree.ts                    дерево Раздела 9 + сценарии
    discovery.ts                        блоки А–Г и правила красных флагов
    glossary.ts                         термины и определения
  core/
    quiz.ts                             подсчёт и проверка ответов
    progress.ts                         схема localStorage, чтение/запись, устойчивость к мусору
    decision-engine.ts                  обход дерева, объяснение отвергнутых веток
    discovery-summary.ts                сборка markdown-сводки и красные флаги
  ui/
    App, Sidebar, SectionPage, Markdown-провайдер
    Quiz, Exam, DecisionTrainer, DiscoveryForm
    Callout, Flow, Facts, TermTooltip, Glossary
```

Разделение ответственности:
- **проза** живёт в `.mdx` и правится как текст;
- **данные** живут в `.ts`, типизированы и провалидированы zod;
- **логика** живёт в `core/` чистыми функциями без React и тестируется без jsdom;
- **UI** в `ui/` не содержит правил предметной области.

Проверка на корректность границ: любой компонент из `core/` должен быть понятен и
тестируем без чтения `ui/`, и наоборот.

## 3. Навигация и прогресс

Модель «книга с сайдбаром»: слева оглавление из 10 разделов плюс экзамен, глоссарий и два
тренажёра; справа — содержимое. Все разделы доступны сразу, ничего не блокируется. Прочитанные
и пройденные помечаются в сайдбаре.

Маршрутизация — по хэшу (`#/section/05-assistants-rag-agents`), чтобы GitHub Pages не требовал
настройки rewrite-правил и чтобы ссылка на конкретный раздел работала.

Прогресс: ключ `afb:progress:v1` в localStorage.

```ts
{
  readSections: string[],
  quizResults: Record<sectionId, { score: number, total: number, answers: number[][] }>,
  examResult?: { mode: 'test' | 'cards', score: number, total: number },
  discoveryDraft?: Record<questionId, string | string[]>
}
```

Данные валидируются zod при чтении. Несовпадение схемы — молча сбрасываем состояние и
продолжаем работу; приложение не должно падать из-за содержимого localStorage.

## 4. Содержание разделов

Тезисы взяты из ТЗ, текст пишем сами.

1. **AI-ландшафт: как устроен рынок.** Различение компании / продукта / модели / платформы.
   ChatGPT против GPT, OpenAI против Azure OpenAI, Claude против Anthropic, что такое Llama.
   Кто такие OpenAI, Anthropic, Google, Meta, Mistral, DeepSeek, Qwen. Разбор ошибки
   «мы будем использовать ChatGPT API».
2. **Как принимать AI-решения через призму бизнеса.** Клиент покупает результат, а не AI:
   выручка, затраты, скорость, ручной труд, риски, клиентский опыт. Практика перевода
   «нам нужен AI» в «какую проблему вы решаете».
3. **Что такое LLM и где заканчиваются её возможности.** Токены, контекст, контекстное окно,
   галлюцинации. Вывод: модель работает с информацией, но не обладает доменной экспертизой
   клиента автоматически.
4. **Из чего состоит AI-решение.** Схема «пользователь → приложение → LLM → данные и
   инструменты». Роли embeddings, vector DB, knowledge base, tool calling, function calling,
   MCP — без деталей реализации.
5. **Ассистенты, RAG и агенты.** Ключевой раздел. 5.1 ассистенты, 5.2 RAG (RAG не обучает
   модель, а даёт ей контекст), 5.3 агенты, 5.4 «когда агент не нужен» — 10 разобранных
   кейсов, где агент усложняет решение без выгоды.
6. **Каталог типовых AI-решений.** Клиентская поддержка, продажи, юридические процессы,
   внутренние знания компании — с указанием подходящего класса решения для каждого.
7. **Экономика AI.** Стоимость токенов, стоимость инференса, почему GPU дороги, когда выгоден
   API, когда оправдан open source. Отдельная глава «почему open source не всегда дешевле»:
   инфраструктура, сопровождение, поддержка, обновления моделей, инженерная команда.
   Врезка со ссылкой на Inference TCO Calculator.
8. **Discovery и сбор требований.** Блоки А (бизнес), Б (процесс), В (данные), Г (ограничения).
   Питает discovery-опросник.
9. **Framework выбора решения.** Дерево: найти информацию → RAG; помочь сотруднику →
   assistant; выполнять действия → agent; фиксированные шаги → workflow. Питает тренажёр.
10. **Типичные мифы AI.** Пять мифов из ТЗ с разбором: «нужна самая умная модель», «агенты
    заменят сотрудников», «RAG обучает модель», «open source всегда дешевле», «AI-проект
    начинается с выбора модели».

## 5. Интерактивные модули

### 5.1 Квиз после раздела

3–5 вопросов, одиночный или множественный выбор. У **каждого** варианта — собственное
объяснение, почему он верен или неверен; именно в этих объяснениях живёт антимаркетинговая
часть методички. Обратная связь показывается сразу после ответа, а не в конце. Перепройти
можно всегда. Результат пишется в прогресс.

### 5.2 Финальный экзамен

Открытые вопросы ТЗ невозможно проверить в статике без бэкенда, поэтому на одном банке из
10 тем делаем два режима:

- **Тест** — сценарные вопросы с выбором («клиент говорит X, что отвечаете»), даёт
  измеримый результат;
- **Карточки** — оригинальная открытая формулировка из ТЗ, кнопка «показать эталонный ответ»,
  самооценка «знаю / не знаю».

Темы: ChatGPT против GPT; модель против продукта; что такое RAG и когда нужен; когда нужен
агент и когда нет; что такое MCP; когда OpenAI, а когда open source; какие данные нужны для
AI-проекта; как оценить ROI; какие вопросы задать клиенту до технологий; какой класс решения
подходит конкретной бизнес-проблеме.

### 5.3 Тренажёр выбора решения

Дерево вопросов из Раздела 9 приводит к одному из четырёх классов: RAG, assistant, agent,
workflow. На листе показываем не только вердикт, но и **почему не остальные три** — это
содержание Раздела 5, поданное как результат собственного выбора пользователя.

Плюс банк из ~8 бизнес-сценариев: пользователь проводит кейс через дерево сам, затем
сверяется с разбором.

`core/decision-engine.ts` — чистая функция `(answers) => { verdict, rejected[], sectionRefs }`.

### 5.4 Discovery-опросник

Четыре блока А–Г с вопросами из Раздела 8. Ответы сохраняются на лету в черновик.

На выходе: кнопка «скопировать сводку» (markdown, готовый для вставки в почту или Confluence)
и версия для печати.

Сверху — индикатор красных флагов, вычисляемый из ответов:
- заявлены персональные данные → облачное размещение под вопросом;
- нет документов и нет CRM → RAG строить не на чем;
- шаги процесса не описаны → разговор об агенте преждевременен;
- нет владельца процесса → нет заказчика результата.

Это связывает Раздел 8 с тренажёром Раздела 9 в один рабочий инструмент.

### 5.5 Глоссарий

Термины размечаются в MDX как `<T>MCP</T>` и берут определение из `data/glossary.ts` —
один источник правды. Всплывающая подсказка по месту плюс отдельная страница со всем словарём.

### 5.6 Экономика без собственного калькулятора

В Разделе 7: как считаются токены, из чего складывается стоимость инференса, таблица цен API.
Затем врезка со ссылкой на https://kryadov.github.io/llm-hardware-calculator/ с объяснением,
что именно этот инструмент считает (полную стоимость самохостинга вплоть до стоек, питания и
людей) и как сравнить его `$/1M токенов` с ценой API. Глава «open source не всегда дешевле»
получает не декларацию, а кнопку «посчитайте сами».

## 6. Достоверность фактов

Главный риск проекта — не код, а факты. Разделы 1, 6 и 7 называют конкретных вендоров,
модели и цены. Материал, написанный по памяти языковой модели, устаревает на месяцы и учит
presales уверенно говорить неправду. В `llm-hardware-calculator` это уже происходило: каталог
моделей был написан из памяти и оказался на 8–11 месяцев несвежим.

Правило: **ни один факт о вендорах, моделях, ценах и лимитах не пишется по памяти.** Каждый
такой блок пишется после сверки с первоисточником — страницами прайсинга и документации
вендоров — и размечается в MDX:

```mdx
<Facts verifiedOn="2026-08-08" sources={["https://…/pricing", "https://…/models"]}>
  …таблица цен…
</Facts>
```

`src/content/facts.test.ts` падает, если хотя бы у одного блока `verifiedOn` старше 90 дней
или отсутствует ссылка на источник. Устаревание должно быть громким, а не тихим.

На странице такой блок показывает видимую плашку «данные проверены 8 августа 2026», чтобы
читатель понимал срок годности.

## 7. Тестирование

Vitest, без jsdom везде, где это возможно.

| Модуль | Что проверяем |
|---|---|
| `core/quiz.ts` | подсчёт баллов, частичный ответ на multi-choice, повторное прохождение |
| `core/progress.ts` | запись и чтение, битые и чужие данные в localStorage не роняют приложение |
| `core/decision-engine.ts` | каждый лист дерева достижим; каждый сценарий даёт ожидаемый класс; список отвергнутых веток непуст |
| `core/discovery-summary.ts` | сборка сводки, срабатывание каждого правила красных флагов |
| `data/*.test.ts` | zod-схемы; у каждого раздела есть квиз; у каждого варианта ответа есть объяснение; ровно один правильный ответ, если вопрос не помечен как множественный |
| `content/facts.test.ts` | свежесть `verifiedOn`, наличие источников |
| `ui/` | smoke-тесты через Testing Library: раздел рендерится, квиз отвечает на клик, тренажёр доходит до вердикта |

## 8. Деплой

`.github/workflows/deploy.yml` по образцу калькулятора: сборка и публикация на GitHub Pages.
Репозиторий публичный, `kryadov/ai-for-business-tutorial`, лицензия MIT.

Если публикуем по тегу, сразу добавляем tag-policy в окружение `github-pages`, иначе первый
релиз упадёт на шаге deploy при зелёном build:

```bash
gh api -X POST repos/kryadov/ai-for-business-tutorial/environments/github-pages/deployment-branch-policies \
  -f name='v*' -f type=tag
```

`CLAUDE.md` импортирует `AGENTS.md`, как принято в соседнем проекте.
