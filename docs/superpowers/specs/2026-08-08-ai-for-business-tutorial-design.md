# AI для бизнеса: от идеи до решения — дизайн интерактивного сайта

Дата: 2026-08-08
Статус: согласовано, готово к планированию реализации

## 1. Что делаем

Статический сайт-методичка на основе ТЗ (`ai_for_business.docx`): 11 разделов прозы,
квизы, финальный экзамен, два рабочих тренажёра. Всё исполняется в браузере, бэкенда нет,
телеметрии нет.

Относительно ТЗ материал расширен по договорённости с заказчиком: добавлены text2SQL как
отдельный класс решения, протокол A2A рядом с MCP и новый раздел о безопасности и guardrails.
Нумерация разделов после шестого сдвинута, см. §4 этой спеки.

Позиционирование берём из ТЗ дословно и выносим на первый экран: методичка не учит писать
код, обучать модели или проектировать архитектуру. Она учит понимать рынок AI, говорить на
одном языке с заказчиком и инженером, находить реальные бизнес-кейсы и отличать работающее
решение от маркетингового обещания.

Аудитория: AI presales, business development, product owners, delivery managers,
руководители направлений, предприниматели, консультанты. Не для data scientists, AI
engineers, ML researchers.

Сайт двуязычный: английский основной, русский второй. Оба языка пишутся нативно от общего
плана раздела — со своими примерами и своей интонацией, а не переводом друг друга. Границы
этой нативности заданы в §10 этой спеки.

### Границы

В объёме:
- 11 разделов прозы по ~1000–1500 слов каждый, на английском и русском;
- квиз после каждого раздела;
- финальный экзамен в двух режимах;
- тренажёр выбора класса решения (Раздел 10 методички);
- discovery-опросник (Раздел 9 методички);
- глоссарий с всплывающими определениями;
- прогресс чтения в localStorage;
- деплой на публичный GitHub Pages.

Вне объёма:
- собственный калькулятор экономики — вместо него ссылка на существующий
  [Inference TCO Calculator](https://kryadov.github.io/llm-hardware-calculator/);
- любой бэкенд, аккаунты, синхронизация прогресса между устройствами;
- проверка открытых текстовых ответов;
- третий и последующие языки;
- выдача сертификатов.

## 2. Стек и структура

**Astro 7 + React 19 в островах + TypeScript + Tailwind 4 + Vitest + zod.**

Выбор объясняется двуязычностью и природой материала. Из одиннадцати разделов проза
составляет подавляющую часть, а интерактив локализован в четырёх местах. Astro отдаёт прозу
статическим HTML без единого килобайта JS и подключает React только на страницах квиза и
тренажёров. Сверх того он закрывает три задачи, которые в SPA пришлось бы писать руками:
маршрутизацию с локалью, загрузку контента по локали и схемную валидацию фронтматтера.

Совместимость проверена, а не предположена: Astro 7 несёт Vite 8 внутри себя, а MDX
подключается собственной интеграцией `@astrojs/mdx`, поэтому конфликта peer-зависимостей с
`@mdx-js/rollup` (который требует Rollup и потому несовместим с Rolldown в Vite 8) здесь не
возникает вовсе.

Версии на дату написания спеки: `astro@7.2.0`, `@astrojs/react@6.0.2`, `@astrojs/mdx@7.0.5`,
`react@19.2.8`, `tailwindcss@4.3.3` через `@tailwindcss/vite`, `vitest@4.1.10`, `zod@4.4.3`.
Astro 7 требует Node `>=22.12.0`.

### Конфигурация

```js
// astro.config.mjs
import { defineConfig } from 'astro/config'
import react from '@astrojs/react'
import mdx from '@astrojs/mdx'
import tailwindcss from '@tailwindcss/vite'

export default defineConfig({
  site: 'https://kryadov.github.io',
  base: '/ai-for-business-tutorial',
  integrations: [react(), mdx()],
  i18n: {
    locales: ['en', 'ru'],
    defaultLocale: 'en',
    routing: { prefixDefaultLocale: true, redirectToDefaultLocale: true },
  },
  vite: { plugins: [tailwindcss()] },
})
```

`prefixDefaultLocale: true` выбран сознательно: оба языка получают префикс, `/en/…` и `/ru/…`
симметричны, корень редиректит на язык по умолчанию. Асимметричный вариант, где английский
живёт без префикса, экономит несколько символов в адресе и создаёт постоянный источник
путаницы в ссылках.

### Структура

```

    decision-tree.ts                    топология дерева Раздела 10 методички + сценарии

    decision-engine.ts                  обход дерева, объяснение отвергнутых веток
    discovery-summary.ts                сборка markdown-сводки и красные флаги
    locale.ts                           хранение выбранного языка и автоопределение
  components/
    Layout.astro, Sidebar.astro, LocaleSwitcher.astro

  islands/

  pages/
    index.astro                         редирект на язык по умолчанию
    [locale]/index.astro                титульная страница
    [locale]/section/[slug].astro       раздел методички
    [locale]/exam.astro, glossary.astro, trainer.astro, discovery.astro
  tests/
    facts.test.ts, parity.test.ts
```

Astro-компоненты в `components/` не гидратируются вовсе. React живёт только в `islands/` и
подключается директивами `client:visible`. Ни один остров не импортирует другой — они
независимы и общаются исключительно через `core/progress.ts`.

Разделение ответственности:
- **проза** живёт в `.mdx` и правится как текст;
- **данные** живут в `.ts`, типизированы и провалидированы zod;
- **логика** живёт в `core/` чистыми функциями без React и тестируется без jsdom;
- **представление** — в `components/` (Astro, без гидратации) и `islands/` (React) — не
  содержит правил предметной области.

Проверка на корректность границ: любой компонент из `core/` должен быть понятен и
тестируем без чтения `components/` и `islands/`, и наоборот.

Ни один модуль из `core/` не знает о языке ничего, кроме кода локали: подсчёт баллов, обход
дерева и правила красных флагов работают со скелетом, а не с текстом. Локализация — вопрос
представления.

## 3. Навигация и прогресс

Модель «книга с сайдбаром»: слева оглавление из 11 разделов плюс экзамен, глоссарий и два
тренажёра; справа — содержимое. Все разделы доступны сразу, ничего не блокируется. Прочитанные
и пройденные помечаются в сайдбаре.

Маршрутизация — настоящие статические адреса, генерируемые на сборке:
`/ai-for-business-tutorial/en/section/05-assistants-rag-agents/` и тот же путь с `/ru/`.
Каждый раздел на каждом языке — отдельный HTML-файл, что важно и для поисковой выдачи, и для
печати, и для ссылки, отправленной коллеге.

Переключатель языка сохраняет текущий раздел: со страницы раздела 5 на английском ведёт на
раздел 5 на русском, а не на главную. Реализуется через `getRelativeLocaleUrl` из `astro:i18n`
и общий `sectionId`, поэтому не может разъехаться при переименовании слагов. `<html lang>`
проставляется из `Astro.currentLocale`.

Язык по умолчанию — английский; корень сайта редиректит на `/en/`. Автоопределение языка
браузера делает небольшой скрипт на титульной странице: при первом заходе, если
`navigator.language` начинается с `ru` и сохранённого выбора нет, он уводит на `/ru/`. Явный
выбор пользователя сохраняется в `localStorage` (`afb:locale`) и дальше главнее
автоопределения.

Автоопределение сознательно ограничено титульной страницей. Скрипт, перебрасывающий читателя
между локалями на произвольном разделе, ломает ссылки, отправленные коллеге, и кнопку
«назад».

Прогресс: ключ `afb:progress:v1` в localStorage. Прогресс общий на оба языка — он привязан к
идентификатору раздела, а не к локали. Раздел, прочитанный по-английски, отмечен прочитанным
и в русской версии.

```ts
{
  readSections: string[],
  quizResults: Record<sectionId, { score: number, total: number, answers: number[][] }>,
  examResult?: { mode: 'test' | 'cards', score: number, total: number },
  discoveryDraft?: Record<questionId, string | string[]>
}
```

Данные валидируются zod при чтении. Несовпадение схемы — молча сбрасываем состояние и
продолжаем работу; приложение не должно падать из-за содержимого localStorage.

## 4. Содержание разделов

Тезисы взяты из ТЗ, текст пишем сами. Ниже — общий план обоих языков: он задаёт, о чём
раздел и какие выводы читатель должен унести. Примеры, формулировки и интонация в английской
и русской версиях свои.

1. **AI-ландшафт: как устроен рынок.** Различение компании / продукта / модели / платформы.
   ChatGPT против GPT, OpenAI против Azure OpenAI, Claude против Anthropic, что такое Llama.
   Кто такие OpenAI, Anthropic, Google, Meta, Mistral, DeepSeek, Qwen. Разбор ошибки
   «мы будем использовать ChatGPT API».
2. **Как принимать AI-решения через призму бизнеса.** Клиент покупает результат, а не AI:
   выручка, затраты, скорость, ручной труд, риски, клиентский опыт. Практика перевода
   «нам нужен AI» в «какую проблему вы решаете».
3. **Что такое LLM и где заканчиваются её возможности.** Токены, контекст, контекстное окно,
   галлюцинации. Вывод: модель работает с информацией, но не обладает доменной экспертизой
   клиента автоматически.
4. **Из чего состоит AI-решение.** Схема «пользователь → приложение → LLM → данные и
   инструменты». Роли embeddings, vector DB, knowledge base, tool calling, function calling —
   без деталей реализации. Отдельная глава о протоколах: **MCP** соединяет модель с
   инструментами и данными, **A2A** соединяет агентов между собой. Показать, что это разные
   уровни задачи, а не конкуренты.
5. **Ассистенты, RAG, text2SQL и агенты.** Ключевой раздел. 5.1 ассистенты, 5.2 RAG (RAG не
   обучает модель, а даёт ей контекст), 5.3 **text2SQL** — вопросы к структурированным
   данным, 5.4 агенты и мультиагентные схемы, 5.5 «когда агент не нужен» — 10 разобранных
   кейсов, где агент усложняет решение без выгоды, включая мультиагентную схему там, где
   хватило бы одного агента.

   Ключевое различение главы 5.3: RAG отвечает по неструктурированным документам, text2SQL —
   по базе и цифрам. «Сколько мы продали в марте» и «что написано в договоре с подрядчиком» —
   это два разных проекта, и путают их постоянно. Здесь же — где text2SQL ломается:
   грязная схема без описаний, отсутствие витрин, вопросы, на которые в данных нет ответа,
   и почему цифру из такого ответа нельзя нести в отчёт без проверки.
6. **Каталог типовых AI-решений.** Клиентская поддержка, продажи, юридические процессы,
   внутренние знания компании, аналитика и отчётность — с указанием подходящего класса
   решения для каждого.
7. **Безопасность и guardrails: почему демо работает, а продакшен нет.** Раздел идёт от риска
   к контрмере.
   - 7.1 **Куда уходят данные.** Облако против VPC против on-prem, обучается ли провайдер на
     данных клиента, хранение и удаление, персональные данные и регуляторика. Те самые
     вопросы, которые пришлёт служба безопасности заказчика.
   - 7.2 **Кто что видит.** RAG наследует права доступа плохо: документ, попавший в индекс,
     доступен всем, у кого есть доступ к ассистенту. Обязательный вопрос на discovery, а не
     деталь реализации.
   - 7.3 **Prompt injection.** Прямая и косвенная — через документ, который модель прочитала.
     Почему «мы запретили это в промпте» не является защитой.
   - 7.4 **Права агента.** Что агент может сделать необратимо: отправить, удалить, заплатить.
     Наименьшие привилегии, подтверждение человеком на необратимых шагах, журнал действий.
     Связка с 5.5: часть случаев «агент не нужен» на деле означает «агенту нельзя столько
     прав».
   - 7.5 **Качество ответа.** Отдельная глава, не сводимая к безопасности: галлюцинации,
     ответы не по теме, неверная тональность, устаревшие данные в индексе. Как качество
     вообще измеряют до внедрения и после, что такое приемлемый уровень ошибки и почему он
     разный для поддержки и для юридического заключения.
   - 7.6 **Guardrails как контрмеры.** Что конкретно ставится в решение: фильтры на входе,
     проверки на выходе, редактирование PII, ограничение тематики, сверка ответа с
     источником, human-in-the-loop. Цена вопроса: guardrails — строка в смете и в сроках, а
     не бесплатная галочка.
8. **Экономика AI.** Стоимость токенов, стоимость инференса, почему GPU дороги, когда выгоден
   API, когда оправдан open source. Стоимость guardrails и проверок из раздела 7 методички входит в
   расчёт. Отдельная глава «почему open source не всегда дешевле»: инфраструктура,
   сопровождение, поддержка, обновления моделей, инженерная команда. Врезка со ссылкой на
   Inference TCO Calculator.
9. **Discovery и сбор требований.** Блоки А (бизнес), Б (процесс), В (данные), Г (ограничения).
   Питает discovery-опросник.
10. **Framework выбора решения.** Дерево: найти информацию в документах → RAG; получить цифру
    из базы → text2SQL; помочь сотруднику → assistant; выполнять действия → agent;
    фиксированные шаги → workflow. Питает тренажёр.
11. **Типичные мифы AI.** Мифы из ТЗ с разбором: «нужна самая умная модель», «агенты заменят
    сотрудников», «RAG обучает модель», «open source всегда дешевле», «AI-проект начинается с
    выбора модели». Плюс миф, выросший из раздела 7 методички: «guardrails добавим потом».

Порядок разделов 7–11 отличается от ТЗ: безопасность вставлена перед экономикой, остальное
сдвинуто. Повествование идёт «что бывает → что нужно, чтобы это дожило до прода → сколько это
стоит целиком → как собрать требования → как выбрать класс → чего не слушать». Мифы остаются
финалом, как в ТЗ.

## 5. Интерактивные модули

### 5.1 Квиз после раздела

3–5 вопросов, одиночный или множественный выбор. Скелет квиза общий на оба языка, текст
нативный — подробности в §10 этой спеки.

У **каждого** варианта — собственное
объяснение, почему он верен или неверен; именно в этих объяснениях живёт антимаркетинговая
часть методички. Обратная связь показывается сразу после ответа, а не в конце. Перепройти
можно всегда. Результат пишется в прогресс.

### 5.2 Финальный экзамен

Открытые вопросы ТЗ невозможно проверить в статике без бэкенда, поэтому на одном банке из
13 тем делаем два режима:

- **Тест** — сценарные вопросы с выбором («клиент говорит X, что отвечаете»), даёт
  измеримый результат;
- **Карточки** — оригинальная открытая формулировка из ТЗ, кнопка «показать эталонный ответ»,
  самооценка «знаю / не знаю».

Десять тем из ТЗ: ChatGPT против GPT; модель против продукта; что такое RAG и когда нужен;
когда нужен агент и когда нет; что такое MCP; когда OpenAI, а когда open source; какие данные
нужны для AI-проекта; как оценить ROI; какие вопросы задать клиенту до технологий; какой
класс решения подходит конкретной бизнес-проблеме.

Три темы из добавленного материала: чем text2SQL отличается от RAG и по каким признакам
выбирать; чем A2A отличается от MCP; какие guardrails закладывать и почему их нельзя
добавить потом.

### 5.3 Тренажёр выбора решения

Дерево вопросов из Раздела 10 приводит к одному из пяти классов: RAG, text2SQL, assistant,
agent, workflow. На листе показываем не только вердикт, но и **почему не остальные четыре** —
это содержание Раздела 5, поданное как результат собственного выбора пользователя.

Развилка «документы или база» стоит рано и разводит RAG и text2SQL: это самая частая ошибка
класса решения на реальных встречах.

Плюс банк из ~8 бизнес-сценариев: пользователь проводит кейс через дерево сам, затем
сверяется с разбором.

`core/decision-engine.ts` — чистая функция `(answers) => { verdict, rejected[], sectionRefs }`.

### 5.4 Discovery-опросник

Четыре блока А–Г с вопросами из Раздела 9. Ответы сохраняются на лету в черновик.

На выходе: кнопка «скопировать сводку» (markdown, готовый для вставки в почту или Confluence)
и версия для печати.

Сверху — индикатор красных флагов, вычисляемый из ответов:
- заявлены персональные данные → облачное размещение под вопросом;
- нет документов и нет CRM → RAG строить не на чем;
- данные только в базе, документов нет → это text2SQL, а не RAG;
- шаги процесса не описаны → разговор об агенте преждевременен;
- нет владельца процесса → нет заказчика результата;
- цена ошибки высокая, а проверяющего в процессе нет → нужен human-in-the-loop, см. раздел 7 методички;
- доступ к документам не разграничен → RAG раздаст их всем, см. главу 7.2.

Это связывает Раздел 9 с тренажёром Раздела 10 и с разделом 7 методички в один рабочий инструмент.

### 5.5 Глоссарий

Термины размечаются в MDX как `<T id="mcp">MCP</T>` и берут определение из
`data/glossary.{en,ru}.ts` по идентификатору — один источник правды на язык. Всплывающая
подсказка по месту плюс отдельная страница со всем словарём.

Набор идентификаторов терминов общий: термин, определённый на одном языке и не определённый
на другом, роняет тест паритета. Английский термин в русском тексте не переводится там, где
он и в жизни не переводится (embeddings, tool calling, MCP), но определение даётся по-русски.

### 5.6 Экономика без собственного калькулятора

В Разделе 8: как считаются токены, из чего складывается стоимость инференса, таблица цен API.
Затем врезка со ссылкой на https://kryadov.github.io/llm-hardware-calculator/ с объяснением,
что именно этот инструмент считает (полную стоимость самохостинга вплоть до стоек, питания и
людей) и как сравнить его `$/1M токенов` с ценой API. Глава «open source не всегда дешевле»
получает не декларацию, а кнопку «посчитайте сами».

## 6. Достоверность фактов

Главный риск проекта — не код, а факты. Разделы 1, 6 и 8 называют конкретных вендоров,
модели и цены. Материал, написанный по памяти языковой модели, устаревает на месяцы и учит
presales уверенно говорить неправду. В `llm-hardware-calculator` это уже происходило: каталог
моделей был написан из памяти и оказался на 8–11 месяцев несвежим.

Отдельно отмечены как быстро меняющиеся и требующие сверки при написании: **статус и
владелец спецификаций MCP и A2A**, состав их внедрений, а также перечень моделей и вендоров
в разделе 1. Это ровно тот материал, который выглядит стабильным и не является таковым.

Правило: **ни один факт о вендорах, моделях, ценах и лимитах не пишется по памяти.** Каждый
такой факт добывается сверкой с первоисточником — страницами прайсинга и документации
вендоров — на дату написания.

**Числа не живут в прозе.** Цены, лимиты контекста и прочие измеримые факты лежат один раз в
`data/pricing.ts` вместе с `verifiedOn` и ссылками на источники; MDX только вызывает
компонент, а локализуются лишь подписи колонок:

```mdx
<PricingTable id="api-token-prices" />
```

Это второй по важности приём двуязычности после теста паритета. Если позволить набирать
таблицу цен в каждом `.mdx` отдельно, английская версия однажды скажет $3 за миллион токенов,
русская — $2.5, и обе будут помечены как проверенные.

Качественные утверждения, привязанные к моменту («у вендора X такой-то профиль»), размечаются
в MDX блоком с той же дисциплиной:

```mdx
<Facts verifiedOn="2026-08-08" sources={["https://…/pricing", "https://…/models"]}>
  …текст…
</Facts>
```

`src/content/facts.test.ts` падает, если хотя бы у одного блока или записи в `pricing.ts`
`verifiedOn` старше 90 дней или отсутствует ссылка на источник — в обеих языковых версиях.
Устаревание должно быть громким, а не тихим.

На странице такой блок показывает видимую плашку «данные проверены 8 августа 2026», чтобы
читатель понимал срок годности.

## 9. Порядок работ

1. Каркас: Astro, MDX, Tailwind, i18n-маршрутизация, переключатель языка, сайдбар,
   прогресс.
2. Раздел 5 целиком на обоих языках — проза, квиз, схемы. Самый содержательный раздел
   (ассистенты, RAG, text2SQL, агенты), на нём проверяем тон и объём в обеих версиях.
3. Просмотр заказчиком. Правки тона и объёма применяются ко всем последующим разделам.
4. Остальные десять разделов, каждый сразу на двух языках. Раздел 7 пишется после раздела 5:
   он опирается на введённые там классы решений.
5. Тренажёр выбора решения и discovery-опросник.
6. Экзамен, глоссарий.
7. Деплой.

Раздел пишется на обоих языках в одном заходе, а не «сначала все английские, потом все
русские». Отложенный перевод при нативном письме превращается в отдельный проект, который
никогда не доделывают.

## 10. Двуязычность: что расходится, а что нет

Оба языка пишутся нативно. Чтобы это не превратилось в два расходящихся продукта под одним
адресом, граница проведена так:

**Расходится текст.** Проза разделов пишется независимо от общего плана: свои примеры, свои
формулировки, своя интонация. Русский раздел про клиентскую поддержку может разбирать кейс
российского банка, английский — американского ритейлера. Объём версий тоже может отличаться.

**Не расходится структура.** Идентификаторы вопросов, число вариантов ответа и ключ
правильных ответов лежат один раз в `data/quizzes/*.ts`; тексты — в `text.en.ts` и
`text.ru.ts` по тем же идентификаторам. Формулировка вопроса своя на каждом языке, но
«правильный ответ — вариант 3» физически не может разойтись. Так же устроены дерево решений
(топология одна, подписи свои) и discovery (правила красных флагов одни, вопросы свои).

**Не расходятся числа.** Все измеримые факты — в `data/pricing.ts`, см. §6 этой спеки.

**Тест паритета** `src/content/parity.test.ts` падает, если:
- у раздела из `sections.ts` нет `.mdx` в одной из локалей;
- у вопроса квиза или экзамена есть текст на одном языке и нет на другом;
- у варианта ответа есть объяснение на одном языке и нет на другом;
- узел дерева решений или вопрос discovery не подписан на одном из языков;
- термин глоссария определён не везде;
- ключ в `ui-strings.en.ts` отсутствует в `ui-strings.ru.ts` или наоборот.

Расхождение объёма и содержания прозы тест не ловит и не должен — это осознанный выбор в
пользу нативности.
